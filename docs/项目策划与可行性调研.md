# DOTA2 键位方案管理工具：项目策划与可行性调研

> 历史调研文档，保留早期方案和验证计划。当前实现、使用说明及验证边界以根目录 [README.md](../README.md) 为准；首版已采用完整 `570` 文件夹备份与迁移方案。

调研日期：2026-10-26。本文是公开资料调研与工程方案，尚未进行当前 DOTA2 客户端、跨账号及 Steam Cloud 的实机验证。

## 1. 项目判断

建议立项为“DOTA2 键位方案管理与迁移工具”，先投入 2–3 个工作日验证导入机制，再决定产品开发范围。

用户的核心需求——保存熟悉的键位、换账号后快速恢复——有可行的工程路径。但“纯网页生成一串文本，直接粘贴控制台，完整恢复所有键位”目前缺少足够的技术依据，不宜作为首版承诺。

推荐架构是：接近游戏设置页的独立前端 + 版本化配置模型 + 文件导入导出；需要简化安装操作时，再增加 Windows 本地助手。经过实测支持的设置，可以额外输出控制台命令。

判断依据分为三类：

- 已查到：公开客户端命令、配置文件结构、官方更新记录与 Steam Cloud 机制。
- 工程推断：本地配置迁移比完全依赖控制台更有希望覆盖完整偏好。
- 待验证：当前版本实际使用哪些配置文件、命令是否可用、跨账号迁移是否持久生效。

## 2. 为什么不能把全部键位直接转换成 bind

### 2.1 游戏存在不同配置层

普通引擎绑定、游戏自己的动作绑定和设置变量，需要分别处理。

公开客户端命令清单包含 `bind`、`exec` 等正式发布命令，但常见的 `dota_ability_execute`、`dota_ability_quickcast`、`dota_item_execute` 等条目带有 `developmentonly` 标记。存在命令名不等于普通玩家能通过它可靠地配置正式游戏中的全部键位。不能根据旧教程直接实现“技能槽 → bind 字符串”的转换。[S1]

Valve 的问题跟踪器中，有用户提交过 `dotakeys_personal.lst` 的实际片段，其中包含英雄标识、技能动作、按键、修饰键和施法模式；另一份报告展示了按物品保存的施法模式。这是键位存在结构化配置的直接用户报告，但不是官方稳定格式协议，也不能证明旧问题在当前版本仍然存在。[S3][S4]

部分全局偏好则通过 ConVar 保存，例如快速施法在按下时触发的选项。首版应逐项判断设置属于哪一层，不能假设全部都在一个文件中。[S2]

### 2.2 三种“导出字符串”必须区分

| 导出物 | 谁能解释它 | 是否有机会直接放进游戏控制台 |
| --- | --- | --- |
| 本工具分享码，例如 `D2KEY1:...` | 本工具解码器 | 不可以据此假设游戏能识别 |
| 真实控制台命令序列 | 游戏控制台 | 只适用于实测支持的设置，并需验证长度、分隔与持久化 |
| 本地 cfg 文件及 `exec 文件名` | 游戏命令执行器 | cfg 必须先放到可读取位置，且内容仍受命令能力限制 |

把 JSON 压缩或编码成 Base64，不会使 DOTA2 获得解码和导入能力。本次未发现可作为产品基础的公开完整键位导入码接口。

`exec` 的用途是执行 cfg 文件；将 `dotakeys_personal.lst` 换个扩展名并不能把结构化配置变成有效控制台命令。也不能假设 `exec https://...` 能在线拉取方案。[S1]

### 2.3 批量安装设置与对局宏是两回事

Valve 在 2016 年的官方更新中限制一个按键绑定多条控制台命令。这不等价于禁止在控制台一次设置多个独立选项；两者必须区分，不能用这一历史限制直接否定配置安装，也不能据此设计对局宏。[S5]

本项目只需要迁移设置，不需要设计一键连招或自动操作。

## 3. 三条实现路线

| 路线 | 用户操作 | 优点 | 主要限制 | 建议 |
| --- | --- | --- | --- | --- |
| 网页 + 控制台导出 | 编辑后复制命令 | 使用门槛低、容易传播 | 完整键位覆盖尚未证实 | 作为经过验证的部分导出能力 |
| 网页 + 配置文件 | 下载配置、按向导放入目标位置 | 能验证结构化键位迁移，无需安装助手 | 路径、账号识别和 Cloud 冲突需要用户处理 | 用于技术验证和首个可用版本 |
| Windows 小应用 | 选择方案和目标账号，备份后应用 | 可处理路径、文件合并、备份和回滚 | 需要额外开发、打包和兼容维护 | 完整体验的推荐方向 |

浏览器扩展不会天然解决游戏目录访问问题；普通网页的本地文件操作需要用户选择或授权，相关浏览器能力还存在兼容差异。可以做“用户选择文件夹后写入”的增强功能，但首版应保留下载和手动导入方式。[S7]

不建议先做注入游戏主界面的插件：本次未找到适合作为该产品基础的官方全局设置扩展接口。独立页面复现设置交互，工程范围更明确。

## 4. 推荐的使用流程

### 首次保存

1. 用户从现有账号导入配置，或从模板开始。
2. 在熟悉的设置布局中编辑技能、物品、单位控制及相关偏好。
3. 工具显示冲突、继承关系与不支持的设置。
4. 保存方案，并导出工具分享码或本地方案文件。

应优先提供“导入已有配置”。让用户在工具中重新输入全部按键，会重复原本想解决的麻烦。

### 换账号恢复

1. 在目标账号完成必要的首次启动，生成配置，再正常退出游戏并等待同步完成。
2. 工具列出本地候选账号和路径，由用户选择目标，不以目录更新时间替用户决定。
3. 读取目标配置，展示本次变化并备份相关文件。
4. 在游戏退出状态应用选定字段。
5. 启动游戏，检查设置与实际操作；退出、同步、重启后再次确认。

这是待实测的产品流程，不是已验证的 Cloud 冲突解决操作指南。若 Cloud 覆盖本地变更，必须先解决同步时序，不能将“文件写入成功”显示为“配置恢复成功”。

Steam 官方文档说明，云存储按用户隔离，并在会话前后进行同步。因此 Steam Cloud 能解释同账号跨设备同步，却不能直接作为跨账号迁移服务；本地写入必须考虑下载旧配置和退出时回写的影响。[S6]

## 5. 首版范围

| 能力 | 优先级 | 验收口径 |
| --- | --- | --- |
| 导入已有键位方案 | P0 | 识别实测版本；未知字段保留或明确阻止不安全转换 |
| 默认技能槽、常用物品槽和单位动作 | P0 | 编辑、导出、导入后界面与实际操作一致 |
| 普通施法、快速施法及相关全局偏好 | P0 | 分别验证绑定和触发行为 |
| 冲突检查与变化预览 | P0 | 区分真正冲突、不同英雄及不同上下文的复用 |
| 本地方案保存、分享码、文件导出 | P0 | 完整往返，无静默丢失 |
| 原配置备份与回滚 | P0 | 恢复本次修改前的配置 |
| 英雄及非英雄单位专属键位 | P1 | 保留继承关系，切换单位不污染其他方案 |
| 按物品覆盖施法行为 | P1 | 与当前客户端字段及行为一致 |
| 控制台命令导出 | P1，取决于验证 | 仅输出验证通过的能力，不支持项单独列出 |
| 云端账号体系、公开方案社区 | 后续 | 有真实分享需求后再做 |

TP、中立物品、额外能力等槽位，应按当前客户端实测建模，不要沿用旧教程中的固定槽位编号。

暂不将画质、分辨率、硬件性能、账号凭证、购买记录等纳入迁移。产品聚焦键位与相关操作偏好。

## 6. 界面与架构

“采用 DOTA2 原生界面”建议落实为：沿用当前设置页的分类、中文术语、按键录入和施法模式交互，用独立前端实现视觉与布局。它不是把游戏设置面板直接嵌入网页。

界面可以保留默认、英雄、其他单位等入口及技能、物品区域，增加方案选择、导入、导出、冲突提示和变化预览。具体排布以实测时的当前客户端为准。官方 2026 Summer Scrub 已增加特定非英雄单位的键位自定义，说明不能只照着旧版设置截图做静态页面。[S8]

建议前端使用团队熟悉的 React 或 Vue + TypeScript；核心配置逻辑独立于界面。若开发 Windows 助手，可选择 Electron 复用 TypeScript，或在有 Rust 经验时评估 Tauri。首版无需业务后端。

建议的数据处理链：

```text
已有配置 / 手工编辑 / 工具分享码
                 ↓
        统一方案模型 + 能力校验
                 ↓
     当前客户端版本适配与差异计算
                 ↓
配置文件导出 / 本地应用 / 已验证的控制台导出
```

方案模型至少保存：格式版本、适配游戏版本、动作标识、作用范围、按键、修饰键、施法方式及相关偏好。

“继承默认”“显式解绑”“自定义覆盖”必须是不同状态，否则容易把英雄专属配置错误地改成空键位。动作和键名使用稳定内部标识，中文只用于显示。

本地应用模块需要处理：Steam 安装目录与游戏库目录分离、目标账号选择、游戏运行状态、只修改受支持字段、备份、写入失败恢复和版本不匹配。不要整体复制整个 Steam userdata 目录，也不要通过修改 Cloud 元数据绕过同步。

控制台导出使用固定模板和允许列表，拒绝在按键等输入中插入额外命令。不要默认使用 `unbindall`，也不要把 `host_writeconfig` 或 `writekeybindings` 的通用说明理解为“完整保存全部英雄键位”的保证。[S1]

## 7. 首先执行的技术验证

建议用两个用户自有、可测试的账号验证。以下是开发前需要完成的实验，本轮尚未执行。

| 实验 | 操作 | 通过条件 |
| --- | --- | --- |
| 配置来源定位 | 分别修改一个技能键、物品键、英雄覆盖和全局偏好，退出后比较相关文件 | 每项能定位到字段及其实际存储位置 |
| 控制台能力 | 对候选命令逐项测试，检查界面和实际行为 | 普通客户端可用，且不依赖开发或作弊模式 |
| 控制台批量导入 | 测试较长命令、分隔、多次粘贴和错误输入 | 无静默截断，部分失败可定位；超限时能分段 |
| 文件往返 | 导入配置、不修改、再导出 | 支持字段语义一致，未知内容不被静默删除 |
| 跨账号迁移 | 将选定字段迁入另一个已初始化账号 | 实际施法、物品和单位操作符合预期 |
| 同步持久化 | 正常退出同步后重启，并切换账号再返回 | 配置仍正确，没有串号或被旧云配置覆盖 |
| 模式与输入边界 | 普通、快速、自施法、修饰键、鼠标侧键、非 US 布局 | 区分支持与不支持行为，不错误宣称成功 |
| 单位边界 | 默认英雄、专属英雄、召唤物及常用模式 | 正确继承；自定义游戏限制单独标明 |
| 回滚 | 应用后恢复备份 | 受影响配置恢复到修改前状态 |

Console 原型的通过条件应是“指定范围内全部设置可迁移并持久保存”，不是“控制台没有报错”。文件方案也必须验证启动后的真实行为，不能仅比对文本。

决策分支：

- 控制台完整通过目标范围：可以优先做网页命令导出。
- 控制台部分通过、文件方案通过：推进网页与 Windows 助手，标明两种导出的覆盖差异。
- 文件迁移被 Cloud 持续覆盖且不能形成可靠流程：暂停完整迁移功能，先保留方案编辑与人工导入引导。
- 导入机制未稳定前，不投入大量时间还原界面。

## 8. 工期与产品价值

以下为一名熟悉前端和 Windows 文件操作的开发者的初步工作量估算，不是固定交付承诺；取决于技术验证结果。

| 阶段 | 估算工作量 | 交付物 |
| --- | --- | --- |
| 技术验证 | 2–3 人日 | 支持矩阵、配置样本、跨账号与同步结论 |
| 网页首版 | 5–8 人日 | 编辑器、已有配置导入、校验、方案保存与文件导出 |
| Windows 应用与验证 | 7–12 人日 | 路径识别、账号选择、备份、应用、回滚与打包 |

Windows 可用首版合计约 14–23 人日。若需要同时完整覆盖所有英雄、非英雄单位、历史配置和多操作系统，工期需要另估。网页首版的范围必须服从前面的导入验证结果。

作为朋友之间使用的工具，值得先做一个小版本。面向公众时，价值主要来自已有配置导入、可靠迁移、差异提示和回滚。相对手动复制配置，工具必须减少出错与排查成本。

尚未做市场规模或付费意愿研究，不据此预测收入。先邀请 5–10 名有迁移需求的用户试用，记录完成时间、恢复错误、不支持设置及回滚使用情况。若用户仍频繁回到游戏逐项重设，核心需求还没有完成。

建议对外定位为“个人键位方案备份、分享与恢复”，覆盖重装、换电脑、临时设备及账号迁移等场景。

## 9. 最终建议

项目可推进，但应先验证迁移能力。首版最重要的成功标准是：导入现有习惯后，可以在目标账号恢复，并在游戏重启及同步后继续正常使用。

“只粘贴一次控制台”可以保留为待验证的理想体验；在获得当前客户端实测结果前，产品应以配置文件迁移为主要技术候选，并允许通过小型 Windows 应用降低操作成本。
